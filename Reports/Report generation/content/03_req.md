## Stakeholders

The requirements in this chapter were derived from the people and organisations who use or supply the system. Their needs differ: citizens want a clear answer about today and tomorrow, agencies want lead time, reviewers want results they can trace, and data providers want their licences respected. Table {tab:stakeholders} lists each group and what it needs, and the functional and non-functional requirements below are written to meet these needs.

!table Stakeholders and their needs | stakeholders | 26,74
| Stakeholder | Needs from the system |
|---|---|
| Citizens and vulnerable groups | Current PM2.5 and AQI for their city, a short-range outlook, plain advice, and a simple explanation of why the air is bad today |
| City agencies and health services | Station-level forecasts at +24 and +48 hours to plan measures before an episode; upwind fire information during the stubble season |
| Researchers and reviewers | A reproducible benchmark with locked splits, documented data, baselines including CAMS, and results traceable to run files |
| Project team | A training pipeline that runs unchanged on a laptop, Kaggle and the GPU workstation, and never touches the test years before model freeze |
| Data providers (CPCB via XKDR, Copernicus, NASA, Open-Meteo) | Use within the licence terms, with attribution and no bulk redistribution where not allowed |

## Functional Requirements

The functional requirements describe what the system must do. They are grouped into the live platform, which serves the public every day, and the forecasting model, which is trained and evaluated offline. Each requirement is stated so that it can be checked by a test or by inspecting a run folder.

**Live platform**

- **FR1. Live data collection.** The backend fetches CAMS PM2.5, PM10, aerosol optical depth, dust, NO2 and CO, together with temperature, humidity, wind and boundary-layer height, for all 33 cities every 12 hours and whenever an operator triggers a refresh. Every request has a timeout, and the result of each source is recorded with its latency so that the dashboard can show which sources are healthy.
- **FR2. Fire information.** The backend fetches NASA FIRMS active-fire detections for the last 24 hours over India and its neighbours. For each city it counts the fires within 300 km, the fires upwind of the city given the current wind, and their total fire radiative power, which the map and the city view display.
- **FR3. Fusion into one tensor.** All sources are aligned to the same 33 cities and the same hours and stored as one tensor of at most 72 hours by 33 cities by 20 features. If a source fails or times out, the last good copy of that source is kept, so a single outage never empties the dashboard.
- **FR4. REST API.** The backend serves health, status, live snapshot, history, archive, tensor, model status and AI endpoints over a REST API. Responses are cached between refreshes, so dashboard requests do not trigger new calls to the data providers.
- **FR5. Dashboard views.** The dashboard shows a national summary, a map with city values, fires, wind and satellite layers, a city view with a four-day outlook and advice, an analysis of the current drivers, a what-if view, the monthly history from the CPCB archive, and a view that explains the data pipeline and the live tensor.
- **FR6. Language-model analyst.** Short insight cards and answers to free-text questions are generated by an LLM from the current numbers. The request goes to Amazon Bedrock first and falls back to Groq if the first provider fails, and the cards are labelled as AI-generated.
- **FR7. Honest labelling.** Every CAMS value is labelled as model output, not as a measurement, and the what-if view is labelled as an illustrative heuristic built on hand-set coefficients from the literature.

**Forecasting model**

- **FR8. Reproducible data download.** All raw data is downloaded by resumable, idempotent scripts. Each file is recorded in a manifest with its SHA-256 checksum, so a rerun skips files that already exist and a corrupted file is detected.
- **FR9. Dataset construction.** The system builds a fixed panel of stations, applies quality control, converts all times to UTC, applies the publication delay of every source, and writes the training, validation and test arrays to one dataset with a documented data card.
- **FR10. Locked test split.** The test split is locked by checksum when the dataset is built. Only the final evaluation script may read it, and only after the team has recorded the model freeze; a test fails if any other code path opens the test arrays.
- **FR11. Configured, traceable training.** Every model is trained from one YAML configuration. The configuration, metrics, predictions and software environment are saved under a unique run identifier that contains the date, the experiment, the seed and the code version, and an interrupted run resumes from its last completed epoch.
- **FR12. Forecast output.** The model forecasts PM2.5 at every hour from +1 to +48 hours for every station in the panel and returns the source-group gate weights with each forecast, so the dashboard can show what the model relied on.
- **FR13. Scoring.** Every model is scored at +1, +24 and +48 hours with RMSE, MAE, R², bias and skill against persistence and CAMS, together with episode scores above 250 µg/m³, AQI-class accuracy and macro-F1, and significance tests between models.
- **FR14. Generated tables.** Every table of results in this report and in the paper is generated from run files by a script, so that no number is typed by hand.

## Non-Functional Requirements

The non-functional requirements describe how well the system must work. For a forecasting study the most important qualities are integrity and the absence of leakage, because a result that uses future information or a number that cannot be traced is worse than no result. Table {tab:nfr} lists the qualities and how each is met.

!table Non-functional requirements | nfr | 22,78
| Quality | Requirement |
|---|---|
| Integrity | No metric is typed by hand; every reported number traces to a `metrics.json` file and its run identifier |
| No leakage | Inputs use only data published before the issue time; wavelets are causal; normalisation uses training years only; targets are never interpolated |
| Reproducibility | Fixed seeds, versioned configurations, a git hash in every run identifier, data manifests with SHA-256 checksums |
| Portability | The same code runs on CPU, Kaggle and a CUDA GPU; the device comes from the configuration |
| Reliability | Training resumes from atomic checkpoints; the live backend falls back to the last good data when a source times out |
| Performance | The live refresh finishes within the 12-hour cycle; dashboard views load from cached API responses |
| Security | API keys live only in untracked environment files and in the hosting provider's secret store; keys are never logged |
| Cost | LLM calls are cached and limited to the refresh cycle and user questions; no LLM calls in tests |
| Usability | Reduced-motion support, light and dark themes, plain-language advice next to every number |

Integrity and leakage are enforced by code rather than by convention. The test suite contains tests that perturb every value after the issue time and check that the model inputs do not change, tests that check that normalisation statistics come from the training years only, and a test that fails if any module other than the final evaluation script opens the locked test arrays. Reproducibility follows from the run identifier: given a run folder, the exact code, configuration and data version that produced it can be recovered. Portability matters because the project moved between a laptop, Kaggle and a GPU workstation during development; the device and the number of data-loader workers are the only settings that change between them.

On the platform side, reliability means that a failing data source degrades one panel instead of the whole dashboard, and security means that no key is ever written to the repository, the logs or the browser. Usability was checked on desktop and phone screens, in both themes and with reduced motion enabled.

## Hardware Requirements

The system needs one machine with a GPU for training, ordinary laptops for development, and two hosting services for the live platform. Table {tab:hardware} lists the hardware that was used.

!table Hardware used for development, training and hosting | hardware | 26,74
| Item | Specification |
|---|---|
| Training workstation | NVIDIA RTX PRO 4500 (Blackwell) with 32 GB VRAM; Intel Xeon, 12 cores and 24 threads; 63 GB RAM; 852 GB free on the system drive and 1.86 TB on a data drive |
| Development laptops | Any recent laptop with 16 GB RAM; used for data scripts, the platform and the test suite on CPU |
| Backend hosting | Render web service (Python runtime, free plan, Singapore region) |
| Frontend hosting | Vercel static hosting with automatic deployment from the main branch |

The model is small (under 250,000 parameters for the full M6), so GPU memory is not the limit. The cost of training lies in the number of runs: baselines, seven ladder rungs, three settings, six ablations and five seeds each. A GPU that can be used for long uninterrupted runs matters more than raw speed. Disk space is the other real requirement: the raw CAMS forecasts, the ERA5 grid and the station archive take several hundred gigabytes before processing, while the processed datasets are small enough to stream from disk during training. The hosting side needs very little: the backend holds one tensor and a cache of API responses in memory, and the frontend is a set of static files.

## Software Requirements

The software stack is open source except for the two hosted LLM services. Python is used for data, models and the backend, and TypeScript for the dashboard. Table {tab:software} lists the main components by layer.

!table Software stack | software | 24,76
| Layer | Software |
|---|---|
| Operating system | Windows 11 (training workstation), any OS for development |
| Language and runtime | Python 3.12, Node.js 22 |
| Deep learning | PyTorch 2.11 with CUDA 12.8 (needed for Blackwell GPUs), PyTorch Geometric |
| Data | NumPy, pandas, PyArrow, xarray, zarr, h5netcdf, netCDF4, SciPy, PyWavelets |
| Classical models and explanations | LightGBM 4.7, SHAP, Captum |
| Data access | cdsapi and the ECMWF data-stores client for Copernicus, httpx for REST sources |
| Experiment tracking and export | run folders with `metrics.json`, MLflow, ONNX and ONNX Runtime |
| Testing | pytest (146 tests) |
| Backend | FastAPI, Uvicorn, httpx, python-dotenv |
| Frontend | Vite 6, React 19, Tailwind CSS 4, Recharts 3, MapLibre GL 6, Three.js, GSAP |
| AI services | Amazon Bedrock (Nova Micro), Groq (gpt-oss models), optional local Ollama |

Two choices in the stack follow from the requirements. The backend keeps its dependencies to FastAPI, httpx and NumPy and never loads PyTorch, because the free hosting plan limits memory; the trained model will be served through ONNX Runtime instead. On the training side, PyTorch had to come from the CUDA 12.8 build, since earlier builds have no kernels for the Blackwell GPU. Large arrays are stored in zarr and opened lazily with xarray, so the data loader reads one window at a time and never holds the full dataset in memory.

## Data Requirements

The model and the platform draw on six kinds of data: station measurements, reanalysis weather, CAMS forecasts, satellite fire detections, live weather and calendar events. Each source was checked for its licence, its resolution and the delay with which it is published, because the delay decides which values may be used at a given issue time. Table {tab:data-sources} summarises the sources.

!table Data sources, use and licence | data-sources | 22,30,20,28
| Source | Used for | Resolution | Licence |
|---|---|---|---|
| CPCB CAAQM via the XKDR India Air Quality Database [@xkdr] | Targets and pollutant history (PM2.5, PM10, NO2, CO, O3) | Hourly, station | CC BY 4.0 |
| ERA5 reanalysis [@Hersbach_2020] | Node meteorology and the gridded fields | Hourly, 0.25° regridded to 0.75° | CC BY 4.0 |
| CAMS global forecasts | Baseline, inputs in S-B, gridded aerosol fields | 3-hourly leads, about 40 km | CC BY 4.0 |
| CAMS reanalysis (EAC4) [@Inness_2019] | Plausibility checks of the gate weights only | 3-hourly | CC BY 4.0 |
| NASA FIRMS (MODIS, VIIRS) [@firms] | Fire counts and radiative power near and upwind of nodes | Per detection | NASA open data with acknowledgement |
| Open-Meteo | Live weather and node meteorology series | Hourly | CC BY 4.0 |
| OpenAQ [@openaq] | Prospective winter test | Hourly | Attribution; no bulk redistribution |
| python-holidays | Holiday and Diwali flags | Daily | MIT |

The station data sets the requirements for everything else. Targets are hourly PM2.5 at 116 stations, so every other source is brought to the same hours and the same node locations: reanalysis and forecast fields are sampled at each node, and fire detections are counted around each node. EAC4 reanalysis is used only to check the plausibility of the gate weights and never as an input at test time, because a real forecaster does not have a reanalysis of the hours it is forecasting.

## Constraints and Limitations

- The public CPCB archive has few stations after December 2024 and none with NO2, CO or O3 in 2025. The test years were therefore set to 2023 to 2024, with a PM2.5-only check for April to September 2025.
- The Copernicus data stores queue requests. A month of CAMS forecasts took close to three hours in the queue, so downloads, not training, set the pace of the project.
- India Meteorological Department data is not openly available at hourly resolution; ERA5 is used instead.
- No traffic counts exist for the study cities; traffic enters only through a proxy.
- The live platform's PM2.5 values are CAMS model output, not measurements, until the trained model is served.
- The backend runs on a free hosting plan, which sleeps after idle periods and limits memory; it must not load PyTorch.

## Assumptions

- CPCB station readings after quality control represent the true PM2.5 at the station.
- The publication delays measured in 2026 (station data one hour, fires three hours, CAMS ten hours after the run starts) also held during 2018 to 2024.
- The 116-station panel is stable enough over 2018 to 2024 that city-level comparisons across years are meaningful.
- The team, not the code, decides when features and the model are frozen.

## Risks and Challenges

The main risks were external: slow data stores, the loss of training time, and the temptation to tune on the test years. Table {tab:risks} lists each risk with the measure that was taken against it.

!table Risks and mitigations | risks | 30,70
| Risk | Mitigation |
|---|---|
| Copernicus queue delays | Downloads started first, two jobs at a time, resumable and idempotent; partial dataset builds used for smoke tests meanwhile |
| Interrupted training runs | Atomic checkpoint after every epoch (`last.pt`) and automatic resume with the same run identifier |
| Test-set leakage | Test split locked by SHA-256 checksum; only `final_eval.py` may read it; tests fail if any other code path loads it |
| Future-information leakage | Unit tests perturb every value after the issue time and check that the inputs do not change |
| Unverified references in the original proposal | All references checked against Crossref and arXiv; eight that could not be found were removed |
| Model underperforms simple baselines | Ladder and ablations show which component helps; all results are reported, including negative ones |
| Exposure of API keys | Keys only in untracked files and the host's secret store; never printed or committed |
